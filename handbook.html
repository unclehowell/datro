Governance

How every Great House Farm site is kept: who decides, how work moves through stages, when to stop and escalate, and how progress is reported. Written for the AI agents that maintain the sites and for the people who supervise them.

Principles (the seven that never bend)
  • Continued justification. Every change serves one purpose: a more accurate, better evidenced account of what happened at Great House Farm (Tŷ Mawr). A change that only restyles a page has no justification.
  • Learn from experience. Read the site's issue and risk log and the last handover before starting. Repeat no closed mistake.
  • Defined roles. Each site has one maintainer at a time. Two agents never edit the same branch in the same session.
  • Manage by stages. Initiate, deliver, close. Each stage ends with a check against the gate below.
  • Manage by exception. Inside the tolerances an agent acts; outside them it stops and reports.
  • Focus on products. The product is the published page and its data file, verified live. A commit is not a product until it serves.
  • Tailor to the site. Each site's procedure (the SOP pages) narrows these rules; it never loosens them.

Family privacy and holdings (standing rule)

Standing rule for every maintainer (project owner, 24 Oct 2026):

  • Do not list or characterise what the family holds, or does not hold, in papers or heirlooms. The only family holdings a public site may name are Mary Williams' statement, family photographs, and William Buckler's diaries.
  • Write no sentence about the family's possession or lack of a document. State the public record and the archive that keeps it instead.
  • Never publish current family addresses, the whereabouts of living family members, or any heirloom and where it is kept.
  • Reason: to avoid inviting a repeat of the events of the 1950s.
  • Sweeps for existing text are run separately; a maintainer adds no such statement and raises any found in the highlight report.
Stages and gates
  1. Start up. Read this handbook, the site SOP, the last handover, the open issues. Fetch the branch head fresh. Gate: you can name the site's source of truth and every file you will touch.
  2. Initiate. Write the change request (what, why, evidence, files, risk). Gate: assurance has reviewed it, or it is a routine fix (class A).
  3. Deliver. Make the smallest change that does the job, on top of the current head. Gate: the content checks pass on the exact new bytes.
  4. Verify. Wait for the deploy, then check live at 390 px and 1280 px, light and dark. Gate: the live page shows the change and nothing else moved.
  5. Close. Log the change, update the issue and risk log, write the handover. Gate: another agent could pick up tomorrow from your notes alone.
Tolerances (act inside, escalate outside)
DimensionTolerance for an agent acting alone
ScopeFixes inside one site: typos, dead links with an obvious live target, banned words in own prose, out-of-step copies of the same fact. Anything else is a change request.
FactsZero. No new fact, date, name, figure or status without a primary source cited in the change request.
DesignZero. The design system is frozen (see each SOP).
TimeA change that is not live and verified within 60 minutes of its first commit is reported as an exception.
RiskAny change that could take a site offline, delete an original or expose a private person stops for approval.
CostZero spend.
Reports
  • Highlight report (per working session, per site touched): what changed with commit and live check, what is next, open issues, tolerances used. Filed in the Project Office.
  • Exception report (when a tolerance is or will be exceeded): the problem, its cause, the options, the recommendation. Work on that item stops until the executive answers.
  • End-stage report (when a change request closes): the product as delivered, its verification, lessons.
  • Handover (end of every session): state of the branch head, anything half done, the next three actions, who else is working nearby.
Issue and risk log format

One row per item, in the site's log (the Project Office registers):

id | date | site | type (issue|risk|question|change) | description | source | owner | status (open|closed|UNRESOLVED) | next action

An item marked UNRESOLVED stays visible on the site wherever the gap matters; it is never filled by inference.

Coordination between agents
  • Fetch the branch head immediately before every edit; commit on top of it; never force-push.
  • Before touching a site, read the shared change feed (watch.bucklerfamily.estate/changes.json). A site changed by another agent in the last day is check-and-report only for you.
  • Never overwrite, revert or reword a commit by the human owner. List any conflict between the owner's text and the evidence in your highlight report.
  • Announce each commit on the change feed with site, summary and commit.
