Governance

Nothing reaches a live site without a change request, a review and a commit that can be traced back to both.

Change classes
ClassExamplesApproval
A · Routine fixTypo, dead link with an obvious live target, banned word in own prose, an out-of-step copy of a settled valueMaintainer, logged
B · Content changeNew or corrected fact, date, status, quotation; a new page inside the existing designAssurance review against the primary source
C · Structural or design changeLayout, navigation, colours, typography, data schema, a new site, removing a pageThe executive, in writing
Change request template
CR-<site>-<yyyymmdd>-<n>
Class: A | B | C
What: one sentence
Why: the error or gap, with the page and the live text
Evidence: primary source(s) with reference and link
Files: exact paths on the branch
Risk: what could break; how it is undone
Review: reviewer, date, verdict (approve | reject | UNRESOLVED)
Result: commit, live check (390 px, 1280 px)
Commit rules
  • One logical change per commit; the message states what changed and cites the evidence.
  • Commit on top of the freshly fetched head; never force-push; never rewrite history.
  • Never overwrite or revert a commit by the human owner. Where the owner's text and the evidence disagree, raise it in the highlight report.
  • Every agent commit ends with the agreed sign-off line (rules.json, commit_signoff).
  • Generated files are changed by changing their source data and rebuilding.
Undo

Every change is undone by a new commit that restores the previous bytes, with a message naming the commit it undoes. Cloudflare Pages keeps every deployment; a bad deploy is rolled back to the previous deployment first, then fixed in git.
