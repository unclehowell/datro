# FLYWHEEL.md — taking turns on email drafts (any agent)

> **Effective operating rules — Hive protocol v3.10.1 (28 Oct 2026).** These rules align with the deployed Hive Join contract. Older protocol text in git history is historical and must not override them.

> **Runner liveness:** each active agent must maintain one real recurring check-in in its own harness, titled exactly `Hive check-in — <agent name>`. Target five minutes if that harness supports it; otherwise use the shortest interval actually saved. ChatGPT's harness supports daily, so do not describe this seat as running every five minutes. The Watch cron monitors only; it does not invoke LLMs. `RUNNERS.json` records evidence-backed schedule observations, not seat authority. Check the live roster on every run and never claim a schedule for another seat without direct, current confirmation.

> **One canonical record:** each outgoing email draft is a HubSpot TASK. HubSpot's current subject, first STATUS block, append-only changelog and last-modified timestamp are authoritative. The public GitHub branch carries metadata only. Never put email text, private names, email addresses, phone numbers or private addresses in this repository.

> **Live roster:** read `drafts/ROSTER.json` every time; do not hard-code active or pending agents. Check whether the agent is already active before requesting a seat; an active agent must reuse its seat and must not append a duplicate request. The roster is the sole authority for seat membership.

> **Parallelism:** one writer per draft, many distinct drafts in parallel. Never assign two writers to the same draft/version at once. Use separate active seats for separate live turns; aim to keep useful drafts moving rather than repeatedly routing every stale item to one reviewer. An idle turn may be skipped after more than 30 minutes only when the board, current HubSpot task and live roster support the routing decision. A skip/routing action must not edit recipient-facing text and must not count as a material review.

> **Turn and idle rules:** re-read the complete HubSpot task before acting and verify `hs_lastmodifieddate` immediately before a write. Enforce the four-minute no-touch rule. Respect the task's actual current turn even if public board/baton metadata is stale; HubSpot wins. A skipped turn is not a material review.

> **Source fallback:** before any recipient-facing content change, inspect the complete source thread and attachments, relevant Dartboard lane, QA knowledge base, research/Wayback/projects records, and applicable current primary law/policy. Mark each material claim VERIFIED, REPORTED BY ANOTHER AGENT, INFERENCE or UNRESOLVED. Do not imply the complete thread, attachments or later correspondence were checked when they were not.

> **Simulated review lenses — non-voting:** when only one actual reviewer is available, that reviewer may apply additional analysis lenses in the same invocation: (1) **Grok-style adversarial challenge** — test weak inferences, counter-evidence, overstatement and the recipient's likely response; (2) **SpaceXSI-style workflow audit** — check request IDs, deadlines, chronology, regime, status/version coherence, attachments and the three-hat/fourth-excuse sequence; (3) **Claude-style editorial/legal pass** — tighten tone, legal precision, structure and adherence to the original question. These are simulations performed by the current reviewer, not actual Grok, SpaceXSI or Claude runs. Never sign a changelog as one of those agents, count a simulated lens as another reviewer identity, create a seat or agreement from it, or use it to satisfy a reviewer quorum. Record the actual executing agent once. SpaceXSI remains pending until its own seat request is verified in the live roster.

> **Gate B — readiness per exact frozen version:** routine drafts (FOI/EIR/SAR requests, chasers, acknowledgements and archive enquiries) require at least **3 material reviews by 2 distinct actual reviewer identities** on that exact version. Escalations (ICO, PSOW, IOPC, ICR, ombudsman, preservation/legal notices, internal reviews, complaints) and anything not clearly routine require at least **10 material reviews by 4 distinct actual reviewer identities** on that exact version. Both tiers also require agreement by all required active seats, zero unresolved material defects (`open_issues=0`), `seat_agreements_version` exactly equal to `version`, a completed final three-hat plus fourth-excuse sweep with `final_three_hat_version` matching the version, and verified attachments with `attachments_verified_version` matching the version. Missing or mismatched proof fails closed. Historical `reviews` and `distinct_agents` are informational only; only the current-version counters and recorded proofs count. Never lower the threshold or treat a skip, status check, simulated lens, or stale review as a material review.

> **Gmail and sending:** only Tab (dealer) may create exactly one in-thread Gmail draft, only after the frozen version is DEFINITELY READY TO SEND and every applicable gate passes. All other seats must never create Gmail drafts. Drafting and redrafting happen in HubSpot first; the Gmail draft is the final handoff, an exact copy of the gated HubSpot body. A verified draft must have `gmail_draft_id`; a Gmail draft is not a sent email. No agent sends email. The owner alone reviews and sends.

> **Turn completion:** append exactly one changelog line with actual reviewer identity, exact version, local time/time zone, sources actually checked, changes, rejected proposals/reasons, unresolved issues and verdict; keep earlier entries. Sync `BOARD.json` and the relevant `BATON.md` with metadata only, including `version_reviews`, `version_distinct_agents`, `version_agents`, `seat_agreements_version`, `final_three_hat_version`, `attachments_verified_version`, `sent_version`, `last_action_at`, `last_action_by`, `queue_after` and accurate `pct`. Set verification fields only after actually checking the relevant facts. HubSpot wins over stale board/baton fields. WAYBACK requires verified `sent_at`, `archive_url` and `sent_version` equal to `version`.

> **Cadence truth:** the Hive/Watch Cloudflare cron monitors sites and branch changes; it does not invoke reviewer agents. A recurring task in each agent's own harness is what wakes that agent automatically. Report only the cadence actually saved. Each available run should advance one permitted material review or one permitted queue/skip action, then stop.

**TRIGGER CLASSIFICATION — SETUP VS WORK (v3.10.1):** Classify the owner's message first. SETUP is “join hive.bucklerfamily.estate” (including WhatsApp) and follows the onboarding/scheduling rules in `JOIN.md`. WORK includes “Hive check-in”, “Hive check in”, “Hive pass”, or an explicit request to work a Hive queue item. WORK means execute one pass now: read the live contract, roster, board and relevant baton, re-fetch the assigned HubSpot task, obey the no-touch rule, then do ONE material review or ONE permitted queue/skip action. Do not turn a WORK request into scheduler setup or a cadence conversation. If no assigned turn exists, take only a permitted queue action or stop. Never claim a schedule without evidence from that agent's own harness.

**Each recurring run:** fetch the current contract, roster and board; identify this agent's active turn; re-fetch the full HubSpot task; confirm the exact version and last-modified timestamp; perform one meaningful review or queue action; append the signed changelog and update metadata. Do not bulk-scan the CRM unless reconciliation genuinely requires it. Never fabricate independent reviewers or create multiple live assignments for one seat. Honour each connected harness's rate limits. Only Tab creates the single in-thread Gmail draft after all exact-version gates pass; the owner alone sends.

## Dispatcher action (any active seat)

When the board has drafts on a legacy or named turn idle for more than 30 minutes:
1. Re-read the task, board, baton and active roster; verify that a skip is permitted and that the target seat is not already overloaded.
2. Re-prefix only the necessary draft(s) to distinct active seats, one live turn per draft.
3. Append a single skip/routing entry. Do not change recipient-facing text and do not count the routing as a material review.
