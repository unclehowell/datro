Pass 2 (Bug) â AI-first â Pool

Same as Pass 1 but the daily blacklist now includes the fix from Pass 1. This guarantees the AI (or pool) produces a different fix. Pool starts from where last pass left off (fix_rotation).

Pass 3 (Bug) â AI-first â Pool â Guaranteed fallback

Last bug pass. If AI and pool both fail, the guaranteed_bug_fallback runs: it searches the branch directory for files with 3+ consecutive blank lines and removes them. This always produces a fix.

Cooldown & Branch Selection

  • 24-hour cooldown per branch, enforced by comparing last GitHub release timestamp against current time
  • Round-robin via rotation_index â starts from index, checks cooldown, picks first available
  • Non-existent branches skipped â git rev-parse --verify check prevents stale reference crashes
  • All on cooldown: sleep until nearest branch is eligible (max 1h sleep; past 1h exits with error)
  • FORCE_BRANCH env var bypasses rotation for manual targeting
  • Per-branch cooldown timestamps persisted in release-state.json

Command Panel (Joystick Control)

The COMMAND cockpit provides real-time joystick control over the flywheel's behavior. The joystick position determines:

  • Bias (1-5): 1 = aggressive progressive changes, 5 = strict conservative/defensive
  • Risk (1-5): 1 = only safe incremental changes, 5 = full experimental mode
  • Steering Direction: N/E/S/W/CTR + diagonals â determines which directional MASTERPLAN files the LLM agent favours
  • Magnitude (0-1): Strength of the steering direction
  • Burst Mode: Bias â¤2 or risk â¥4 auto-advances gear for faster releases

The joystick state is stored in KV via the /__bias endpoint. The flywheel's agentic loop reads bias on every run and weights directional MASTERPLAN files accordingly. Visual steering blocks (coloured bars) are injected into branch index.html based on the active steering direction.

Agentic Loop (ReAct Pattern)

Each branch release now runs through an autonomous agent with 6 tool-use iterations. The agent can:

  • read_file â read any file from any branch in the repo
  • write_file â write and commit changes directly to GitHub
  • search_code â regex search across all files in a branch
  • run_scan â MCP accessibility/performance scan (EAA, AccessScore)
  • honcho_memory â read/write durable peer observations via Honcho API
  • wallet_info â query deterministic branch wallet (HKDF-based Ed25519)
  • brainstorm â ask the LLM for creative/strategic thinking
  • gitlawv_bounty_* â claim, list, and submit $GITLAWB bounties on Base L2

If the agent produces no valid changes, the system falls back to the best-practice engine (curated checklist of 20+ practices from MDN, web.dev, OWASP, WCAG), and finally to an audit-only release.

Branch Wallet System

Each of the 21 branches has a deterministic crypto wallet derived from a master seed using HKDF (SHA-256):

  • Address: SHA-256 hash of the derived key, truncated to 20 bytes â 0x{40 hex chars}
  • Compute Budget: Last 4 bytes of HKDF output mod 10000 â 0-9999 "compute units" per branch
  • Caching: Wallets cached in KV for 24h, regenerated on cache miss

The wallet system powers the $GITLAWB bounty ecosystem: during each release cycle, the agent can claim bounties, complete work, and submit for payout. The wallet address identifies the branch on the gitlawb node (Base L2), and compute budget influences gear advancement.
